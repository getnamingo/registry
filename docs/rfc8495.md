# RFC 8495 allocation tokens

Apply the corresponding `database/migrations/rfc8495.{mariadb,postgres}.sql` to **existing** registries before upgrading the EPP server. New installations already contain the columns. Back up the database first.

A token is bound to a **canonical lowercase FQDN** in `domain_name`, not a bare label. After migrating, inspect any legacy label-only rows and manually assign the correct zone. Active legacy tokens with NULL `expires_at` remain usable until revoked; assign expiries or deprecate them according to local policy.

The registry setting `allocationTokens` must be `on`. The token may be required for `create` when a domain is reserved or has any token configured for create, and for `transfer` when that domain has a transfer-enabled token. Invalid, used, or expired tokens cannot be used, even if supplied for otherwise available names. A token is consumed atomically on successful create/application submission or transfer request. A later rejected transfer does not automatically reinstate its token; the registry operator must issue another.

Optional JSON restriction columns must be JSON **arrays**, not objects:
* `registrars`: EPP clID strings (e.g. `["RegistrarA"]`).
* `tlds`: zone strings (e.g. `[".example"]`).
* `eppActions`: `["create"]`, `["transfer"]`, or both. A NULL action list means create-only (legacy token behavior); transfer allocation must be explicit. A transfer token is consumed on request and does not block normal future transfers once used.

Only the sponsoring registrar can request the active token via `<allocationToken:info/>`. The control panel assigns a default expiry of 30 days after association; an operator may override it through SQL. Credentials are redacted from EPP transaction logs after upgrade; older logs require separate retention review.
