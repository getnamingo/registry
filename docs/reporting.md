# ICANN Specification 3 reporting (Namingo Registry)

The reporting job is `automation/reporting.php`.

The automated job `automation/reporting.php` writes one **Registry Functions Activity**
CSV and one **Per-Registrar Transactions** CSV per delegated top-level zone, for the
previous complete UTC month. `automation/cron.php` already schedules the script on
the first day of each month when `cron_gtld_mode` is enabled.

This implementation does not silently substitute zero for unknown DNS/WHOIS
measurements or fabricate historical domain totals. Its preflight checks will
stop the run if the required input is unavailable.

## Configuration

The regular Namingo 1.0.37 migration installs reporting history for MariaDB
and PostgreSQL; new installations include it in the main schema. Docker
upgrades run the same migration. No separate reporting SQL installation is
needed. Keep the database/session timestamps and PHP configured for UTC, and
retain the reporting history and EPP transaction logs.

Configure the existing keys in `automation/config.php`:

   ```php
   'reporting_path' => '/opt/reporting',
   'reporting_upload' => false, // keep false until CSVs are reviewed
   'reporting_username' => 'ICANN_API_LOGIN',
   'reporting_password' => 'ICANN_API_PASSWORD',
   // Existing cron_gtld_mode enables the monthly reporting job.
   ```

The first eligible month is the **first complete UTC calendar month after
the upgrade**. Reporting older months is blocked because historical deletions
and transfers cannot be reconstructed from the current registry tables.

## Required per-zone service metrics

Each month, deposit one file, generated by your authoritative DNS servers,
WHOIS services, and CZDS/ZFA source, into `reporting_path/metrics`:

`/opt/reporting/metrics/example-202612.json` for the December 2026 report
of `.example`:

```json
{
  "zfa-passwords": "CZDS",
  "whois-43-queries": 13872,
  "web-whois-queries": 0,
  "searchable-whois-queries": "",
  "dns-udp-queries-received": 500000,
  "dns-udp-queries-responded": 499000,
  "dns-tcp-queries-received": 2200,
  "dns-tcp-queries-responded": 2198
}
```

Replace the example with actual **per-TLD, monthly** counters, not overall
server totals. `""` is permitted for an unavailable WHOIS service as specified
by ICANN; `"CZDS"` is permitted for `zfa-passwords` when applicable. Counts
must otherwise be nonnegative integers. Counter collectors should rotate at UTC
month boundaries and persist the closed month's totals independently of the
report generator. **The report job never resets live service counters.**

If the registry operates more than one delegated top-level zone, Namingo's
host/contact EPP objects do not contain per-TLD assignments. Supply all
`srs-host-*` and `srs-cont-*` fields in each zone's metrics JSON from a
per-zone logging/attribution source. The script deliberately rejects the
multi-TLD report until these fields exist; otherwise every zone could receive
identical, incorrect counts. In a one-TLD registry, these fields are derived
from its EPP transaction log.

If you know the actual number of operational registrars at the period's end,
`"operational-registrars"` can be supplied as another integer field. Otherwise
Namingo counts rows in its `registrar` table. The registrar names and IANA IDs
are likewise taken from the current registrar table; historical rename/ID
changes are not tracked by the migration and should be reconciled manually.

## Generate, inspect, and submit

Run from the installed Namingo environment (with PDO drivers, `ext-dom`, and
Composer dependencies):

```sh
php /opt/registry/automation/reporting.php --month=2026-12 --no-upload

# Inspect both CSV files under /opt/reporting before allowing a submission.
# Submit exactly the same reporting month:
php /opt/registry/automation/reporting.php --month=2026-12 --upload
```

The default is the previous complete UTC month. ICANN Specification 3 file names are
`example-activity-202612.csv` and `example-transactions-202612.csv`.
Uploads use ICANN's `YYYY-MM` period URL, basic authentication, `text/csv`,
and check the XML result code `1000`. Failure aborts with a nonzero exit status;
HTTP 429 and 5xx errors are retried. `reporting_upload=true` enables uploads
for the existing monthly cron invocation. Keep false until reports are verified.

## Important data boundaries and reconciliation

- Domain and host month-end inventory, deletion, transfer and RGP events rely
  on the **new database history triggers**. Statements in `statement` supply
  creation/renewal terms, including multiple renewals of one domain.
- Attempts and SRS commands come from the EPP transaction log, which must be
  retained for the entire month. Missing logs mean undercounted activity.
- A domain create/delete can occur through the control panel rather than EPP;
  inventory and event history capture it, but `attempted-adds` is defined as
  EPP create attempts and does not count panel API attempts. Reconcile panel
  operations if they are used for production gTLD registrations.
- Transfers settled by automated lifecycle processing have event history even
  when the settlement itself does not produce an EPP `transfer` command.
- **Disputed transfer outcomes** have no event source in Namingo's current
  schema and therefore remain zero. Do not submit those zeros when actual
  disputed-transfer decisions exist: extend the integration or reconcile them
  in the CSV before submission.
- Financial statements, audit retention and registrar data must be maintained.
  This patch cannot retroactively reconstruct previously purged records.
- Grace-period reporting uses your configured grace days. A change to those
  settings during the period requires reconciliation against the period's
  actual contractual terms.

Review the resulting CSV values against ICANN Registry Agreement
Specification 3 and your own source-of-truth operational records before the
first production submission. No live ICANN acceptance test is included.
